# POSTGRESQL PORTABILITY

> EUAS Application -- Schema Version 12

## Overview

The EUAS application uses SQLite as its default database backend with a PostgreSQL compatibility layer implemented in `app/database.py`. PostgreSQL mode is activated by setting the `EUAS_DATABASE_URL` environment variable to a `postgresql://` or `postgres://` connection string.

The compatibility layer translates SQLite-specific SQL constructs to PostgreSQL equivalents at runtime, allowing the same application code to run against both backends without manual schema rewrites.

---

## Construct Translation Table

### Mitigated Constructs

These SQLite constructs are translated automatically by the compatibility layer. No application code changes are needed.

| SQLite Construct | PostgreSQL Equivalent | Translation Function | Status |
|------------------|----------------------|---------------------|--------|
| `INSERT OR IGNORE INTO t(...)` | `INSERT INTO t(...) ... ON CONFLICT DO NOTHING` | `_pg_insert_or_ignore()` | Mitigated |
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `SERIAL PRIMARY KEY` | `_postgresize_schema()` | Mitigated |
| `?` bind placeholders | `%s` bind placeholders | `_pg_sql()` | Mitigated |
| `cursor.lastrowid` | `SELECT LASTVAL()` | `PostgresCursor.lastrowid` property | Mitigated |
| `PRAGMA table_info(t)` | `information_schema.columns WHERE table_name=?` | `_table_columns()` (dual path) | Mitigated |
| `BEGIN IMMEDIATE` | `SELECT pg_advisory_xact_lock(key)` | `_acquire_migration_lock()` | Mitigated |
| `sqlite_master` | `information_schema.tables WHERE table_schema=current_schema()` | `_apm_condition_reliability_valid()` (dual path) | Mitigated |
| `conn.executescript(sql)` | Split on `;` and execute each statement individually | `PostgresConnection.executescript()` | Mitigated |
| `REAL` column type | `DOUBLE PRECISION` | `_postgresize_schema()` | Mitigated |

### Not Mitigated Constructs

These SQLite constructs have no PostgreSQL equivalent and are not translated. Any application code or migration that uses them will fail on PostgreSQL.

| SQLite Construct | Issue | Mitigation |
|------------------|-------|------------|
| `julianday()` | SQLite-only date arithmetic function | Avoid in new code. Use Python-side `datetime` arithmetic or `EXTRACT(EPOCH FROM ...)` in PostgreSQL. |
| `date('now','localtime')` | SQLite-specific date function with timezone behavior | Use `NOW()` or `CURRENT_TIMESTAMP` for PostgreSQL. The application currently does not use this in any migration or query that runs on PostgreSQL. |
| `AUTOINCREMENT` keyword | Not valid in PostgreSQL (handled by translation layer, but raw DDL must not use it) | Already mitigated by `_postgresize_schema()`. |

## Translation Details

### 1. INSERT OR IGNORE

**SQLite syntax:**
```sql
INSERT OR IGNORE INTO table_name(col1, col2) VALUES(?, ?)
```

**PostgreSQL equivalent:**
```sql
INSERT INTO table_name(col1, col2) VALUES(%s, %s) ON CONFLICT DO NOTHING
```

**Implementation:** The `_pg_insert_or_ignore()` function in `app/database.py:31-38` detects `INSERT OR IGNORE INTO` (case-insensitive), strips it, converts `?` to `%s`, and appends `ON CONFLICT DO NOTHING`.

**Limitation:** The translation assumes the conflict is on the primary key or a UNIQUE constraint. It does not support `ON CONFLICT(column)` specificity. This is acceptable for EUAS because all `INSERT OR IGNORE` calls target tables with unique constraints on the primary key or a unique column.

### 2. INTEGER PRIMARY KEY AUTOINCREMENT

**SQLite syntax:**
```sql
id INTEGER PRIMARY KEY AUTOINCREMENT
```

**PostgreSQL equivalent:**
```sql
id SERIAL PRIMARY KEY
```

**Implementation:** The `_postgresize_schema()` function in `app/database.py:41-44` uses a regex to replace the pattern. This runs during `executescript()` calls, which is used for DDL execution.

### 3. Bind Placeholder Conversion

**SQLite syntax:**
```sql
SELECT * FROM users WHERE id = ? AND active = ?
```

**PostgreSQL equivalent:**
```sql
SELECT * FROM users WHERE id = %s AND active = %s
```

**Implementation:** The `_pg_sql()` function in `app/database.py:20-28` replaces `?` with `%s`. This is applied to all SQL executed through `PostgresConnection.execute()` and `PostgresConnection.executemany()`.

### 4. lastrowid Emulation

**SQLite behavior:**
```python
cursor = conn.execute("INSERT INTO t(...) VALUES(...)")
new_id = cursor.lastrowid  # Returns the rowid of the inserted row
```

**PostgreSQL equivalent:**
```python
# PostgresCursor.lastrowid property executes:
# SELECT LASTVAL()
# to retrieve the auto-generated ID from the last INSERT.
```

**Implementation:** The `PostgresCursor` class in `app/database.py:47-80` wraps the psycopg cursor and provides a `lastrowid` property that calls `SELECT LASTVAL()` on first access.

**Caveat:** `LASTVAL()` returns the last value generated by a sequence in the current session. If no sequence was used in the last INSERT, it raises an error. This is safe in EUAS because `lastrowid` is only accessed after INSERT statements that generate a serial ID.

### 5. PRAGMA table_info Translation

**SQLite syntax:**
```sql
PRAGMA table_info(users)
```

**PostgreSQL equivalent:**
```sql
SELECT column_name FROM information_schema.columns
WHERE table_schema = current_schema() AND table_name = 'users'
```

**Implementation:** The `_table_columns()` function in `app/database.py:150-153` checks `DB_BACKEND` and uses the appropriate query. This function is used by `_ensure_schema_columns()` and migration validators.

### 6. Migration Lock

**SQLite syntax:**
```sql
BEGIN IMMEDIATE
```

**PostgreSQL equivalent:**
```sql
SELECT pg_advisory_xact_lock(0x455541530010)
```

**Implementation:** The `_acquire_migration_lock()` function in `app/migrations.py:195-208` uses the appropriate lock mechanism per backend. The advisory lock key `0x455541530010` is a fixed constant ensuring only one migration runs at a time across all sessions.

### 7. sqlite_master Translation

**SQLite syntax:**
```sql
SELECT name FROM sqlite_master WHERE type = 'table'
```

**PostgreSQL equivalent:**
```sql
SELECT table_name FROM information_schema.tables
WHERE table_schema = current_schema()
```

**Implementation:** The `_apm_condition_reliability_valid()` function in `app/migrations.py:105-124` has dual-path logic that queries the appropriate system catalog based on the backend.

### 8. Executescript Emulation

**SQLite behavior:**
```python
conn.executescript("CREATE TABLE t1(...); CREATE TABLE t2(...);")
```

**PostgreSQL equivalent:**
```python
# PostgresConnection.executescript() splits on ';',
# strips whitespace, and executes each statement individually.
```

**Implementation:** The `PostgresConnection.executescript()` method in `app/database.py:97-106` splits the script on `;`, filters empty statements, and executes each via a new cursor. The schema is first passed through `_postgresize_schema()` for DDL translation.

| Category | Status |
|----------|--------|
| DDL (CREATE TABLE, CREATE INDEX) | Fully mitigated |
| DML (INSERT, UPDATE, DELETE) | Fully mitigated |
| Schema introspection | Fully mitigated (dual-path queries) |

| Advanced SQLite features | Not mitigated (JSON functions, FTS, R-Tree) |

## Known Non-Portable Code Paths

### 1. julianday()

**Used in:** No current migration or production query uses `julianday()`.

**Risk:** Low. If a future migration introduces `julianday()`, it will fail on PostgreSQL.

**Recommendation:** Use Python-side datetime arithmetic or PostgreSQL-native `EXTRACT(EPOCH FROM interval)`.

### 2. date('now','localtime')

**Used in:** No current migration or production query uses this construct.

**Risk:** Low. The `now()` function in `app/database.py:138-139` uses Python's `datetime.now().isoformat()`, which is backend-agnostic.

**Recommendation:** Always use `NOW()` or `CURRENT_TIMESTAMP` for PostgreSQL, or generate timestamps in application code.

### 3. JSON Functions

**Status:** SQLite-specific JSON functions (`json_extract`, `json_group_array`) are not used in any migration. The application stores JSON as TEXT and parses it in Python.

**Risk:** None currently. If future migrations use SQLite JSON functions, they will need PostgreSQL `->`, `->>`, or `jsonb_*` equivalents.

## Testing PostgreSQL Compatibility

To verify the application works with PostgreSQL:

```bash
# 1. Set up a PostgreSQL database
export EUAS_DATABASE_URL="postgresql://user:pass@localhost:5432/euas_test"

# 2. Run the test suite
python -m pytest tests/

# 3. Verify migration status
python -c "from app.migrations import migration_status; from app.database import db; print(migration_status(db().__enter__(), backend='postgresql'))"
```

The test suite in `tests/test_database_adapter.py` specifically tests the PostgreSQL compatibility layer.

## Future Portability Considerations

| Area | Recommendation |
|------|---------------|
| New migrations | Always write DDL that is compatible with both backends. Use `CREATE TABLE IF NOT EXISTS` and avoid SQLite-only pragmas in migration scripts. |
| Date arithmetic | Use Python `datetime` module for all date calculations. Avoid backend-specific date functions in SQL. |
| JSON storage | Continue storing JSON as TEXT and parsing in Python. If native JSON support is needed, use `jsonb` on PostgreSQL and `json()` on SQLite. |
| Full-text search | If FTS is needed, implement a separate search backend (e.g., Elasticsearch) rather than relying on SQLite FTS5 or PostgreSQL `tsvector`. |
| Stored procedures | Avoid stored procedures. All business logic should remain in application code for portability. |
